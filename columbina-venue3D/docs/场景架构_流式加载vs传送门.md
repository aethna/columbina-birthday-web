# 场景架构：无缝大地图（按玩家距离流式渲染） vs 传送门（一场景一加载）

> 回答用户 m09585 任务3 的 ④。
> 本文只依据**本仓库已经读过的代码与实测量**，不引用外部猜测。
> 数据获取日期：2026-10-07。硬件基准：RTX 4070 Ti SUPER，1400×900 @dpr1，无头 Edge 153（`--disable-frame-rate-limit`）。

---

## 0. 结论先行

**走「无缝大地图 + 分区流式」，不要做传送门。**
但不是因为「无缝更高级」，而是因为**这个项目已经把最难的一半做完了**：

> **地面层（地形 + 草 + 天空）现在就已经是一个以玩家为圆心、可以无限延伸的世界了，而且是零 CPU 内存代价。**
> 缺的只有「道具按距离加载/卸载」这一层——那是个可以增量做的小工程，而传送门会把这半成品作废。

再加一条本项目特有的理由：**会场道具是 26 棵树 + 18 块石头 + 9 丛灌木（53 件）**，
就算全部常驻，代价也远低于一次场景切换带来的加载停顿。
在这个量级上，传送门省不下任何东西，却额外付出「黑屏加载」的体验代价。

如果将来真有「进到室内」这种**无法共处一地**的场景，也用**坐标传送**（把玩家挪到 x += 10000 的空地上，仍然只有一个渲染管线、一个 App 状态），不要做两套场景管理器。详见 §3。

## 1. 现状盘点：哪些已经免费拿到了

### 1.1 地面层 = 已经是「无限世界」

| 事实 | 出处 |
|---|---|
| `useGridSnapping({camera, grassAreaSize, onSnap})` 每帧算 `Math.floor(camera.position.x / gridCellSize)`，格子一变就把草场与地形**重新对中到相机** | `src/core/utils/gridSnapping.ts` |
| `gridCellSize = 80 / 1024 × 1 = 0.078 m` ⇒ 走路时**几乎每帧**都在重新对中，玩家永远在草场正中间 | 同上 + `src/components/grass/core/config.ts` |
| 草场每格 **1024 × 1024 = 1,048,576 株**，覆盖 **80 × 80 m** | `config.ts: DEFAULT_BLADES_PER_AXIS / DEFAULT_GRASS_AREA_SIZE` |
| 草的实例数据由 **compute shader 生成** ⇒ **不在 CPU 内存里**，不存在「走到哪生成到哪」的 CPU 成本 | `config.ts` + 草组件 |
| 地形是一块 `planeGeometry([80, 80, 128, 128])`，靠 `useGridSnapping` 同样对中；高度由 `getTerrainHeight(uTerrainAmp, uTerrainFreq, uTerrainSeed)` 在 **shader 里**位移 | `src/components/Terrain.tsx` |
| 地形圆外由 `opacityNode = 1 - step(grassAreaSize*0.5, length(positionLocal.xy))` 裁掉 ⇒ 是一块**跟着你走的圆盘**，看不出接缝 | 同上 |
| LOD：`[{segments:15, min:0, max:5}, {segments:5, min:5, max:20}, {segments:2, min:20, max:∞}]` | `config.ts: DEFAULT_LOD_SEGMENTS_CONFIG` |

**这意味着「按玩家距离逐渐渲染」这件事，在地面层已经实现，而且是 GPU 侧实现的**（比《我的世界》那种 CPU 分块生成更省）。换场景时你根本不需要重做这一层。

### 1.2 性能余量（实测）

| 草株数 | FPS |
|---|---|
| 20 万 | 1606 |
| 100 万（当前缺省） | **308** |
| 400 万 | 97 |

⇒ 当前 100 万株只花掉约 **3.2 ms/帧**。16.6 ms 的 60 fps 预算里，**地面几乎不占钱**。
钱都花在别处（道具、角色、后处理）。这决定了下面的取舍。

### 1.3 哪些**没有**流式

| 对象 | 现状 | 规模 |
|---|---|---|
| 会场道具 | `/venue/manifest.json` **一次性全量加载**，常驻 | `?real=1`：26 树 + 18 石 + 9 灌木 = 53 件（环形布局，半径 29 m）<br>`?real=0`：原神 OBJ **131 件 / ~775k 三角 / 11 材质 / 19.36 MB** |
| 角色 | 一个 PMX，常驻 | `少女.pmx`：55,943 顶点 / 80,794 三角 / 742 骨骼 / 26 材质 / 15 贴图 |
| 天空 | TSL 渐变 + 星空，纯 shader | 0 成本 |
| 道具的贴图 | 11 张 png + 11 张 `_nra.png`（亮度派生的法线+粗糙+AO） | 随道具一起加载 |

**所以「要流式的是什么」非常明确：只有道具（以及将来可能有的建筑/舞台）。**

### 1.4 现成的挂点

- `src/components/WorldController.tsx` 里 `<AsyncCompile id="grass" onReady={setComponentReady} debug={debugMode}>` —— **这就是「预编译 / 预热」的现成位置**。道具流式加载的「提前量加载」可以挂在它同一套机制上。
- `T_FREEZE` / `uTime`（`src/core/shaders/uniforms.ts` + `WorldController.tsx:147-161`）已经在管全局时间，是「加载期间暂停世界」的天然开关。

## 2. 两条路线的真实成本

### 路线① 无缝大地图（按玩家距离流式渲染）

**要做什么**

1. **空间分桶**：把道具按网格（建议 32 m 一格，与 80 m 草场成整数比）分到 bucket 里，每个 bucket 记 `{ url, 位置, 旋转, 包围盒 }`。这步是纯数据整理，**在构建期就能生成**（`_tools/venue-assets.py` 已经在做类似的事）。
2. **距离驱动加载/卸载**：`R_load = 60 m`、`R_unload = 80 m`（**必须留滞回带**，否则站在半径上会反复加载卸载，帧率会抖）。
3. **每帧预算**：限制「同时在跑的加载数」（比如 2 个）和「每帧最多上传的三角数」。这条是**防卡顿的关键**——一次性塞 20 MB 模型进去就是一次 200 ms 的掉帧。
4. **卸载要真的 release**：`geometry.dispose()` + `material.dispose()` + `texture.dispose()`。WebGPU 下不 dispose 会一直占 VRAM。
5. **预加载**：玩家朝某方向走时，把前方 2 个 bucket 提前排队（可复用 `AsyncCompile`）。

**代价**：约 2～4 天的代码量（分桶脚本 + 一个 `PropStreamer` 组件）。**没有新的技术风险**，全是常规工程。

**收益**：
- 场地可以做到「走一天都走不完」，年会规模变大也不用改架构。
- **零加载画面**。对同人线上活动来说，「点进去就能走」比什么都重要。
- 地面层的 LOD 已经验证过这套思路在这个项目上跑得通。

### 路线② 传送门（一场景一加载）

**要做什么**

1. 场景清单（JSON）+ 一个 `SceneManager`。
2. 进/出传送门时：淡出 → 卸载当前场景全部对象 → 加载新场景 → 淡入。
3. 每个场景各自管理天空/光照/雾/道具/出生点。

**代价**：代码量**更少**（约 1 天），但要处理的是**体验和状态**问题：
- 每次切换都有可见的黑屏/淡入淡出（模型 19 MB + 11 张贴图，本地磁盘也要几百毫秒，网络分发就是秒级）。
- 「场景」这个概念会渗进所有组件：天空要能换、光照要能换、角色位置要重置、物理/布料要重置、`uTime` 要不要重置……**每一处都是一个 bug 的入口**。
- 传送门本身需要美术（门/光柱/提示 UI），否则玩家不知道往哪走。

**收益**：切换瞬间可以完全释放显存；适合「场景之间毫无空间关系」的情况（比如从月球传送到飞船内部）。

### 对比表

| | ① 无缝流式 | ② 传送门 |
|---|---|---|
| 代码量 | 中（2～4 天） | 小（1 天） |
| 加载停顿 | **无**（后台异步） | 每次切换都有 |
| 场景数量上限 | 不受限 | 每加一个都要配 |
| 显存占用 | 常驻「看得见的 + 预加载的」 | 峰值低（但切换时翻倍） |
| 架构侵入性 | 低（只动道具层） | **高**（天空/光照/雾/角色/物理全要能热换） |
| 适合本项目吗 | **适合**：地面层已就绪，道具量小 | 不划算：省不下资源，却多付体验与复杂度 |
| 技术上更「高级」吗 | 否。这是**更朴素**的选择（少一层间接） | 否。传送门只是「用加载掩盖空间不连续」 |

**关键判断**：传送门存在的唯一理由是**空间上真的连不起来**（室内/异世界/不同重力）。
本项目的场景（主会场、舞台、花园、观星台）**都在这颗月球的地表上，天然连续** ⇒ 没有理由把连续的东西切成不连续的。

## 3. 我的建议：混合方案「分区流式 + 坐标传送」

三层，从便宜到贵，**按需要才往下加**：

### 第 1 层：一切都放在同一个无限地面上（现在就该做）

- 地面/草/天空：**已经就绪，不要动**。
- 会场道具：改成 §2① 的流式。
- 「场景」= 一个 JSON 预设：`{ 天空模式, 太阳/月亮参数, 雾色, 道具清单, 出生点, 相机入场路径 }`。
  切换场景 = **插值这几个 uniform**（几帧内平滑过渡），而不是卸载重载。
  因为草和地形是 shader 生成的，「换一个场景」在这个架构里本来就只是**换几个参数**。

### 第 2 层：真的连不起来的地方 —— 用「坐标传送」而不是「第二套场景」

把玩家送到 `x += 10000` 的空地上，那里预先摆好另一个「会场」。
- 仍然是**同一个渲染管线、同一份 `WorldController`、同一个角色实例**；
- 不需要 `SceneManager`，不需要热换天空/光照（那些是 uniform，照样插值）；
- 卸载/加载交给第 1 层同一套流式逻辑（「传送后玩家附近的 bucket 自然会被加载」）。

**这就是「传送门」的全部好处，却没有它全部的代价。**

### 第 3 层：如果将来真有室内

室内可以就是地面上的一个 box（只不过外面包一层不透明外壳挡住草地）。
真的需要「室内独立光照/独立雾」时，再用**淡出 0.2 s → 挪坐标 → 淡入 0.2 s**，成本已经降到几乎为零。

## 4. 落地清单（按优先级）

| 优先级 | 事项 | 说明 |
|---|---|---|
| P0 | 道具空间分桶 | 构建期把 `manifest.json` 切成 32 m 的 bucket，输出 `manifest.buckets.json` |
| P0 | `PropStreamer` 组件 | 距离 + 滞回带（load 60 m / unload 80 m）+ 每帧预算（≤2 个加载在飞） |
| P0 | 真的 `dispose()` | 卸载必须释放 geometry/material/texture，否则 VRAM 会一直涨 |
| P1 | 场景 JSON 预设 | 把「天空模式 / 光照 / 雾 / 道具集 / 出生点」抽成配置，切换 = 插值 uniform |
| P1 | 行进方向预加载 | 用玩家速度方向把前方 bucket 提前排队，复用 `AsyncCompile` |
| P2 | 坐标传送 | 需要独立场景时才加；实现成「挪坐标 + 淡入淡出」 |
| P2 | 可见性剔除 | 道具量变大后加（视锥 + 遮挡），目前 53 件不需要 |

## 5. 坑与判据（写下来免得再踩）

1. **滞回带不是优化，是必需品。** 只用一个半径 ⇒ 站在边界上会每帧加载/卸载，帧率抖成锯齿。
2. **`dispose()` 必须配对。** WebGPU 下泄漏的是显存，不 dispose 只会越跑越慢，而且**不会有任何报错**。
3. **不要在加载回调里同步上传大几何。** 一次 20 MB 的上传就是一次掉帧；要按「每帧最多 N 个 bucket / 最多 M 万三角」切片。
4. **`AsyncCompile` 是预热，不是加载。** 它解决的是「第一次渲染这个材质要编译 shader」的卡顿，不解决「模型还没下载完」。
5. **判据（沿用本项目的 J）**：「参数打印正确 ≠ 功能生效」。流式加载的验收必须量**实际 draw call / 三角数随距离的变化**，不能只看日志说「已卸载」。
6. **地面层的对中是 `Math.floor(pos / cell)`，不是 `Math.round`** ⇒ 相机走过一个格子时会有一次 0.078 m 的跳变。当前看不出来（草本身就杂乱），但如果将来地面要放「对齐到格子的建筑」，这个跳变会露馅。
7. **本项目没有 git。** 改架构前后**手动复制目录存档**（参考 `公用区\存档\步态V1_20261007\`）。
